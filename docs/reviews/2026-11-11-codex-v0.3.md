**v0.3 比 v0.2 完整很多，但还不适合直接冻结为上线规格。** 出金正常路径、四层幂等、Postgres 驱动支付主路径已明显改善；主要缺口集中在拉款退回、数据库权限边界、恢复协议和共享银行账户备选方案。

“只运行 3 天”应成为顶层约束：**减少长期运营建设，增加上线前验证、确定性演练、静态归档和退出机制。** 短期运行不能简化资金正确性，因为一次失败就可能占掉整个展示窗口。

以下只评审文档，未修改文件。P0 表示首次公开上线阻断项，P1 表示重要正确性或可用性缺口，P2 表示范围与表达问题；文档缺口不等于代码已经实现错误。

## B. v0.3 新引入或仍存在的错误、矛盾

### B1. P0｜§5.1–5.3、§5.7、§8：拉款退回仍未形成完整会计闭环

- **问题：**
  1. §5.1 说 Increase 早到的 return 仍对应原交易和退回交易；§5.3 却允许“结算前退回 → failed → 冲正 accept”。这混淆了**通知先到**与**现金从未发生**。
  2. 结算后退回没有释放该笔仍有效的 restriction。
  3. 乱序补账只提到缺 settle，没有提到创建响应丢失、accept 也尚未记账。
- **具体失败场景：** 拉款 $100 受理、结算后仍全额限制，deposit=$100、restriction=$100。此时退回只借客户／贷银行，deposit 变零，restriction 仍为 $100，available 变成 −$100，凭空形成冻结。另一场景是 return 先到，内部只冲正应收，但银行实际产生两笔现金交易，交易级对账持续报漏账。
- **建议修改：** 按现金事实区分：
  - **确认未形成现金交易的拒绝／取消：** 冲正 accept，结束 restriction。
  - **存在原交易与退回交易的 return：** 补齐缺失的 accept、settle，再记独立 return。
  - return 与该笔剩余 restriction 的终止必须同事务完成，保留审计记录。
  - 正常到期释放应依赖结算事实；结算前释放只能走明确的提前可用政策。
  
  `apply_bank_fact` 应计算“缺哪些会计效果”，而不是只沿状态图向前走一步。Increase 明确说明早到 return 仍会先结算，再创建抵消交易。[官方生命周期](https://www.increase.com/documentation/sending-ach-transfers)

### B2. P0｜§2.1、§4.3、§4.5、§12.1：`SECURITY DEFINER` 可实现，但当前权限规格不足以支撑 RLS 与封闭承诺

- **问题：** 函数只检查“所有科目属于同一账套”，未检查“该账套属于当前获授权空间”。如果 `ledger_owner` 同时拥有表，通常会绕过 RLS。`effect` 合法也不等于分录科目、金额和业务依据合法。
- **具体失败场景：** 调用方传入另一个空间的两条科目，函数发现它们属于同一账套，于是成功记账；或者提交一笔借银行／贷客户的平衡分录，没有任何银行交易事实，仍通过所有列出的检查。
- **建议修改：**
  - 明确表属主、函数执行角色、迁移角色和应用角色；运行角色不得具有 `BYPASSRLS` 或可切换到 owner 的权限。
  - 给出明确的函数内空间授权检查；需要时使用 `FORCE ROW LEVEL SECURITY`，不能只写“用了 RLS”。
  - 同事务设置事务局部空间上下文，覆盖连接池复用、worker 和 webhook；跨空间引用使用复合外键等约束。
  - 固定安全 `search_path`，撤销默认 `PUBLIC EXECUTE`。
  - 明确余额检查、业务效果校验由哪层保证。通用平衡分录函数不能单独保证“不超支”和“有经济依据”。

  **txid 方案本身不是不可行。** 它能阻止后来事务追加，但同一事务内 txid 不变，因此不能证明“一次函数调用结束就封闭”。在严格权限下可以作为辅助检查；正文应明确封闭时点、禁止修改已封闭 journal，并避免“任何人都不能追加”这种包含属主在内的绝对承诺。[PostgreSQL 函数安全](https://www.postgresql.org/docs/16/sql-createfunction.html)、[RLS 规则](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)

### B3. P0｜§2.1、§7、§12.3、§15.2：共享银行账户不能作为独立账套方案的透明降级

- **问题：** metadata 只能帮助归属交易，不能隔离银行 current/available balance、funds hold 或账户级限额。
- **具体失败场景：** A、B 各有独立账套，却共用一个银行账户。每个账套的 bank 余额都无法单独等于该账户余额；A 的拉款 hold 又可能占用 B 的出款容量。删除 A 的账套后，共享银行账户仍保留相关历史与余额。
- **建议修改：** 三天首版采用**预创建、数量固定的独立账户池**，满额后展示回放。若必须共享，应作为另一种正式架构：增加账户级控制账、空间分配子账、集中流动性与汇总对账，重写 §7、§12.3。不要等 M2 才确认这一基础假设。

### B4. P1｜§4.3、§5.6、§5.10：锁排序不一致，“可重入”不能解决整体锁顺序

- **问题：** 外层按客户 ID 排序，函数按 account ID 排序，两者不一定一致。函数每次只锁当前 journal 的科目，也没有规定多 journal 事务如何处理共享 bank、receivable、pending 科目。
- **具体失败场景：** 补记多个会计效果时，两个事务先持有不同科目，再互相等待对方持有的科目；数据库中止其中一个。没有明确重试边界时，演练表现为随机失败或任务滞留。
- **建议修改：** 采用稳定的客户资金锁行，统一排序；明确非客户科目的锁层级，以及多 journal 事务的完整锁顺序。声明隔离级别、锁后重新读取的规则，死锁时重试整个数据库事务。外部银行调用继续使用已持久化的原参数和原键。

这主要是可用性与协议完整性问题；不能仅凭排序不同断言一定发生超额支付。

### B5. P0｜§5.8–5.9、§12.4：错误分类、租约接管与 PITR 恢复没有闭合

- **问题：** “同键重试得到明确拒绝”未定义错误类型；普通冲突、限流、参数不一致和明确未创建不能混用。PITR 后只重拉银行交易，也恢复不了尚未结算的银行受理请求。
- **具体失败场景：** 数据库恢复到创建 transfer 之前，银行已经受理出金但尚无 posted transaction。重拉交易发现不了它；客户重新操作生成新 transfer ID，银行接受第二笔。旧 worker 在租约失效后返回，也可能错误覆盖新 worker 的任务状态。
- **建议修改：**
  - 建立适配器错误分类：确定未创建、结果未知、参数冲突、暂时错误；只有有依据的未创建才能释放资金。
  - 明确幂等保证的适用范围与恢复时限，超出已验证保证时停止自动重发。
  - 任务完成使用租约 token／generation 条件更新；过期 worker 的银行响应仍可作为事实摄入，但不能任意修改任务归属。
  - PITR 后先关闭写入，恢复请求身份和银行 transfer 映射，查询未结算资源、处理 unknown，再重拉交易对账。
  - 无法证明恢复完整时，三天项目直接切静态回放，比带着不确定状态继续接受写入更合适。

同键同参数重试方向正确；需要补的是它与恢复、错误分类的接口合同。[Increase 幂等说明](https://www.increase.com/documentation/idempotency-keys)

### B6. P1｜§12.2、§13.1：Cloudflare 有一处确定配置错误，两处路由契约缺口

- **问题：**
  - 免费版 **Bot Fight Mode 不能用 WAF 规则按 webhook 路径跳过**。
  - 全站使用 Full，以忽略 GitHub Pages 证书问题，会放弃源站证书身份验证；ALB 已有 ACM 证书却也未要求验证。
  - 只有 FastAPI `root_path`，没有说明哪一层去掉 API 前缀、保留 Host／协议以及处理 SPA 深链。
- **具体失败场景：** webhook 被质询而反复重试；首页正常但 OpenAPI、刷新 `/app` 或 webhook URL 返回 404；Cloudflare 到源站只有加密而缺少正确身份校验。
- **建议修改：** 免费方案明确关闭 Bot Fight Mode，采用可验证的限流与签名策略；或者使用支持路径跳过的产品。ALB 回源要求 Full (strict)，不要靠全站降低校验解决博客证书维护。补一张“外部路径 → Worker → ALB/nginx → ASGI 路径”映射，并实际验证尾斜杠、查询参数、深链、文档和 webhook。

  还要明确 `fern-origin` 的 DNS／代理方式；若 Worker 直接访问 DNS-only ALB，不能想当然地认为其回源一定满足 Cloudflare IP 白名单。

  [Bot Fight Mode 限制](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/)、[Full 的行为](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full/)、[FastAPI 代理前缀](https://fastapi.tiangolo.com/advanced/behind-a-proxy/)

### B7. P1｜§5.9：按 aggregate version 丢弃旧事件，会删除合法时间线

- **问题：** 只有“完整最新状态快照”才适合直接忽略旧版本；时间线追加、通知等增量事件不适用。
- **具体失败场景：** v3 settle 先到，消费者更新最高版本；v2 accept 后到，被当过期事件丢弃，调查页面永远缺少银行受理步骤。
- **建议修改：** 按消费者定义语义：时间线按 event ID 去重并保留所有事实；快照投影才允许覆盖旧版本；必须顺序处理的增量投影应检测缺口、缓冲或从 Postgres 重建。补充消费者租约、shard checkpoint 和 dead-letter 后的恢复规则。

### B8. P1｜§4.5、§6.1、§7.1–7.2：对账公式比上一版清楚，但接口尚不能执行它

- **问题：** 要比较截点 T，`get_balances(account)` 却没有 `at_time`；journal 时间写银行业务时点，也未明确是否等于银行交易创建时点。“资产覆盖”还混合了总账资产与流动性判断。
- **具体失败场景：** T 后新增一笔交易，内部只算到 T，却拿银行当前余额比较，制造假差异。客户借方余额已作为应收资产展示，但覆盖报表完全忽略它，又没有说明这是保守风险口径。
- **建议修改：**
  - 接口增加 `get_balances(account, at_time=T)`；Increase 实际支持 `at_time`。
  - 银行现金按对应银行 Transaction 的入账时点和 ID 记录，定义截点完整性与迟到数据重跑规则。
  - 分开报告：**总账恒等式、客户负债资产覆盖、即时出款流动性**。前者包含客户应收、资本、损失与 suspense；风险覆盖明确应收折扣；流动性使用银行 available 和已承诺出款。
  - 冻结输入不能仅保存哈希，还要能重现对应原始数据。

  [Increase 余额查询接口](https://www.increase.com/documentation/api/accounts)

### B9. P1｜§5.4、§5.6：平台垫资只有限额，没有并发容量账

- **问题：** `equity:platform_capital` 是累计资本科目，不代表当前仍可动用的现金；没有定义提前可用额度的占用、持续时间及损失后扣减。
- **具体失败场景：** 两笔拉款同时读取剩余垫资 $100，各释放 $100。或者已经核销损失，却仍按最初注资额继续提前可用。
- **建议修改：** 为银行账户／资金池建立原子容量预占，定义 restriction 释放、转出、结算、银行 hold 解除、退回及核销对容量的影响。三天首版可以只开放一个小额固定演练空间，仍须保留这个容量闭环。

### B10. P1｜§6.2–6.3、§8：原签名重放与验签防重放冲突

- **问题：** Increase 的签名包含时间戳，推荐校验时间窗口；旧原文和旧签名不能作为任意延迟的外部 webhook 重放方案。
- **具体失败场景：** 保存十分钟前的 webhook 做乱序演练，正常验签器拒绝；为了让演练成功而取消时效校验，又削弱了公开入口。
- **建议修改：** 公网始终正常验签和检查时间；**验证成功后**保存原文，再由受控内部工具向事实处理层重放。若测试公网签名行为，应使用新的合法测试投递。另明确 proxy 合成的“未转发故障”是传输层失败，不冒充银行业务拒绝。[Increase webhook 验证](https://www.increase.com/documentation/webhooks)

### B11. P1｜§9.4：AI“硬预算”的最坏成本公式不完整

- **问题：** `max_tokens × 单价 × 最大步数` 只覆盖输出时，漏掉长时间线、工具结果以及多轮重复输入；Redis 重启或计数丢失后的行为也没定义。
- **具体失败场景：** 每次只输出少量文字，但每轮重新输入大量调查资料，实际费用持续超过预占。
- **建议修改：** 分别限制输入、输出、工具结果和总轮数；按具体模型价格预占完整上界，涵盖重试。预算状态不可用时停止付费调用；使用持久化支出记录，Redis 做原子预占。三天改为**整场预算＋每日预算**，模型 ID 和调用能力上线前做冒烟验证。

另外，§8“bank 科目只变动一次”应改为：**每个银行交易只入账一次，write-off 不动 bank**。完整的拉款、转出、退回演练本来就有多次合法现金变动。

## C. “只运行 3 天”带来的设计调整

### C1. P0｜§0、§12.3、§13.1、§14：缺少关闭协议，也没有关闭后的作品形态

- **问题：** 目标仍写“长期运行”，空间生命周期却延伸到 30 天；整套 AWS 删除后，现有路径将回源失败。
- **具体失败场景：** 面试官第四天打开简历链接，只看到 502；第三天最后一小时产生的转账仍在 unknown，服务已被删除。
- **建议修改：** 增加明确的 `live → draining → archived` 全站生命周期。静态站应在上线前完成，并独立于 AWS 托管，例如 GitHub Pages。

关闭后的 `waken.dev/apps/fern/` 应继续返回正常页面，包含：

- 明确的运行日期、归档日期，以及“冻结快照／回放”标记。
- 3 分钟英文录屏：正常转账、吞响应恢复、拉款退回、AI 带引用调查。
- 可交互的冻结时间线：银行事实、journal、客户余额、hold/restriction 和对账结果可以互相跳转。
- 一份作者演练空间的脱敏数据快照、参考模型结果、运行规格和测试报告；不公开访客明细、会话或原始签名。
- 代码、英文 README、架构和已知限制。
- 作者可执行的重建入口：固定镜像、IaC、迁移、种子、账户映射与健康检查，并展示一次实际重建耗时。

“一键重新拉起”应由作者触发，不能让匿名访客直接创建 AWS 资源。重建使用新的运行标识，旧归档保持不变。

### C2. P1｜§3、§14：发布计划应收敛为一次可完整展示的交付

- **问题：** v2/v3 仍像长期产品路线图，英文 README 和视频甚至排到最后。
- **具体失败场景：** 三天服务正常，但面试官错过窗口，没有视频与归档；作者最后一天还在补第二适配器。
- **建议修改：**
  - **保留：** Python/FastAPI 单体、Postgres、Redis、EKS，一个 Increase 适配器、确定性 simulator、完整账务、对账、两个核心演练、一个 AI 调查。
  - **简化：** Kinesis 只展示一个可重建的非资金投影；监控使用固定看板；maker-checker 保留最小可信演示。
  - **移到未来工作：** Column、Go 拆分、Tempo/Loki、完整 KYC、自动日报和大运营后台。
  - **提前到发布门槛：** 英文 README、视频、静态归档和销毁脚本。
  - M0 占位页静态托管，不提前消耗 AWS 运行窗口。

### C3. P1｜§12.4、§13.3、§15：长期运维条目应删减，恢复与销毁验证反而要前置

- **问题：** 月度成本、季度演练、支持期提醒和临时开关 Multi-AZ 不符合三天项目节奏。
- **具体失败场景：** 上线才第一次恢复数据库；演示期间切 Multi-AZ 产生变更风险；删除 EKS 后 ALB、卷、快照继续收费。
- **建议修改：**
  - “每季度恢复演练”改为**公开前完成一次实际恢复，并记录耗时**；RPO/RTO 写目标和实测，不直接宣称已达到。
  - “30 天清除”改为**关站导出、验证、脱敏、销毁**流程。
  - EKS 支持期 CI 提醒改为**本次上线前确认版本处于标准支持**。
  - 去掉演示期间临时升降 Multi-AZ；提前确定配置并完成演练。
  - 月度预算改为整场账单：运行小时、预热、恢复演练、额外资源和残留费用。仅按文档现有数字比例，AWS 72 小时约 $20–23，但这不是完整报价。
  - 若要求 AWS 完全关闭，长期归档不能只放 S3/RDS 快照；导出后验证非 AWS 副本可用，再删除残留资源。

### C4. P1｜§2.1、§5.11、§8、§15.2：sandbox 能力确认必须成为最早门槛

- **问题：** 开户限额、API 速率、funds hold 和模拟能力仍是待办；三天没有等待支持回复或自然结算的余地。
- **具体失败场景：** 第一天账户数耗尽；访客等不到初始注资；低风险提前可用演练被银行 hold 阻断；上线跨周末或银行假日，正常到账时间超过关站时间。
- **建议修改：** AWS 启动前完成契约探针，实测开户、注资、settle、return、funds hold、Plaid processor token 和 webhook。预创建有限账户池，设置全站创建上限；满额或外部故障时切明确标注的回放／simulator。

模拟时间推进与真实银行日历必须分开显示，不得把 sandbox 主动 settle 表述为真实 ACH 几秒到账。若运行日期接近文档日期，11 月 11 日本身就值得专门检查银行假日日历。

### C5. P1｜§13.1、§14：DNS 与冷启动风险应在窗口外验证、窗口内预留

- **问题：** 迁移整站 DNS、启用代理、部署 Worker 和首次拉起 EKS 集中在上线当天。
- **具体失败场景：** DNSSEC／记录迁移问题影响博客和邮件；新证书未准备好；ARM 镜像、Pod Identity、External Secrets 或 ALB readiness 首次失败，半天窗口消失。
- **建议修改：** 提前完成 Cloudflare DNS、证书及静态路由验证，核对 MX/TXT/CAA/DNSSEC 和博客深链；关站时只切应用路由，不迁回 nameserver。镜像预构建并验证 ARM，公开前预热数据库、Redis、应用和 AI；三天窗口不使用 Spot、不主动缩容，保留稳定副本。

如果 AWS 总寿命严格只有 72 小时，预热与销毁也应计入这 72 小时，不能把它们隐含放到“免费”的前后两天。

### C6. P1｜§10、§12.3、§14：告警和空间期限需要匹配个人值守能力

- **问题：** “差异超过一天才告警”在三天里太慢；而 24 小时自动只读可能恰好让返回查看的面试官无法再试。
- **具体失败场景：** 第二天产生异常，第三天才报警；作者夜间离线时公开写入持续累积 unknown。
- **建议修改：** 关键演练与真实异常分开标记；非预期账务冲突立即通知作者，unknown、inbox 积压和对账差异按分钟级侦测。首版不承诺个人连续 72 小时值守：公布交互值守时段，无人值守时暂停新资金操作，继续提供回放；已经受理的任务继续自动处理。

空间访问期限按演示窗口配置，重要展示空间一直保留到归档；“只读”只禁止新操作，不能停止既有银行事实的处理。

### 建议的 72 小时上线与值守计划

以下按 **AWS 总寿命 72 小时**设计；因此对外交互时间会短于 72 小时。

| 时间 | 计划与门槛 |
|---|---|
| 启动前一周至前一天 | 本地完成参考模型、乱序、并发和崩溃测试；确认 sandbox；提前迁移 DNS；发布静态占位与归档骨架；准备视频和固定镜像 |
| H0–H4 | 创建 AWS 环境、迁移、账户池与预热；完成公网签名、路由、空间隔离、两项核心演练和对账；验证恢复路径。未过门槛则保留静态站 |
| H4–H68 | 开放交互；每天公布值守时段。开窗前、关窗后和每次演练后检查账本与银行侧结果；冻结功能变更，仅修阻断问题 |
| 故障期间 | 按影响暂停新操作，保留证据；超过预设恢复时限就切回放，避免把全部时间耗在现场修复 |
| H68–H71 | 停止新空间和资金请求；排空任务、处理 inbox、最终对账；导出快照并验证静态回放。未决项如实列明，不强改成成功 |
| H71–H72 | 切静态归档并验证关键 URL；禁用外部 webhook 投递；按依赖顺序销毁 AWS，检查 ALB、EBS、IPv4、日志、快照等残留 |
| 关闭后 | 查看最终账单和归档链接；如需再次演示，由作者启动新一轮部署 |

必须在 AWS 关闭前验证归档。如果仍有未决 sandbox 项目，可以留下明确的终止边界和证据快照；不能声称关闭后仍持续接收银行事实。

**最该先改的 5 件事：**

1. **修好拉款退回闭环：** 按真实现金事实补账，原子结束 restriction，覆盖 accept／settle／return 全部乱序。
2. **写实数据库安全边界：** 完成 `SECURITY DEFINER`、RLS、空间授权、锁顺序和 journal 封闭的具体契约。
3. **取消共享账户的透明降级：** 立即验证 sandbox，采用有限独立账户池及明确的回放降级。
4. **补齐恢复协议：** 明确 unknown 错误分类、租约接管，以及 PITR 后未结算银行请求的恢复方法。
5. **把三天生命周期放到 §0：** 静态归档、视频、停止写入、最终对账、销毁和重建一起成为首次上线门槛。
