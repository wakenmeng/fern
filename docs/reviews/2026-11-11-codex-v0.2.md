这份设计选对了展示主题，但**目前还不能支撑“账一分不差、生产级 ACH 后端”的承诺**。最明显的问题是：基础设施写得很具体，资金状态与会计规则却没有闭合。懂账本和 ACH 的工程师会优先追问这些缺口。

以下评审针对 [docs/DESIGN.md](/Users/waken/workspace/show_green/docs/DESIGN.md)，未修改任何文件。P0 表示核心正确性或公开上线的阻断项；P1 表示重要缺陷；P2 表示可信度和表达问题。未写清的部分按设计缺口处理，不推断代码一定实现错误。

**1. P0｜§4.1–4.3、§5.2：出金 clearing 类型与余额符号不一致**

- **问题：** `clearing:ach:outbound` 被定义为资产，但提交分录贷记它，形成正常贷方余额；同时，posting 使用“借正贷负”，客户负债余额天然为负，`available = posted − holds − unavailable_inbound` 却没有说明是否先做方向归一化。
- **失败场景：** 客户存入 $100，客户科目的分录汇总为 −$100；直接代入公式会显示负余额。出金提交后，报表又可能把 $100 应付款解释成负资产。
- **建议修改：** 将出金 clearing 明确定义为正常贷方的“待结算出金负债”；客户余额明确使用 `−sum(postings.amount_minor)`，或统一提供按科目方向归一化的余额。客户科目改名为 `customer:{id}:deposit`，避免把账面余额与 available 混为一谈。

**2. P0｜§5.1–5.2：提交时扣客户可以成立，但失败补偿分录缺失**

- **问题：** 银行受理后“借客户／贷 clearing”是可行的内部会计政策，含义是把客户存款负债转为支付义务；它不等于现金已经离开银行。文档允许 `submitted → failed`，却没有对应分录。
- **失败场景：** 客户 $100，提交出金后客户余额变为零，银行随后在实际出网前拒绝。若只标记 failed 或释放已释放的 hold，客户的钱永远回不来。
- **建议修改：** 明确触发扣账的是“银行 API 创建成功”还是“实际提交 ACH 网络”。已经扣账但确认未发生现金划转的失败，应借 clearing／贷客户；尚未扣账的拒绝只释放 hold。每个状态转换都列出状态、hold、分录和 outbox 的原子变更。

**3. P0｜§5.2：退回分录只在特定前提下正确，不能直接称为原 journal 的冲正**

- **问题：** 结算后的“借 bank／贷 customer”可以正确抵消整笔出金的净影响，但它不是提交 journal 或结算 journal 任一单笔的精确反向分录。
- **失败场景：** return webhook 先到、settlement webhook 后到，系统直接给客户加钱；原出金现金扣账尚未入账，FBO 现金被虚增。若通用冲正逻辑又反转原 journal，还会重复恢复余额。
- **建议修改：** 把 return 建模为独立资金事件，关联 transfer、原银行交易和退回银行交易；精确冲正另用明确语义。乱序时先补齐原支付的会计事实，再记 return。退回通知与现金返还的入账依据也必须明确。

**4. P0｜§1.1、§5.3：核心入金流程没有分录设计**

- **问题：** 文档重点宣传 ACH debit 风险，却没有发起、受理、结算、可用、拒绝、退回的分录；工资类 inbound credit 也没有完整流程。
- **失败场景：** 未结算入金既计入 posted，又漏写 unavailable，客户立即转走；或者入金尚未进入 posted，却先扣 unavailable，把原有存款也锁住。
- **建议修改：** 选定并写完整一种模型。例如：受理时借入金应收 clearing／贷客户，同时锁定该笔金额；结算时借 bank／贷 clearing；可用性释放只调整限制；结算前失败与结算后退回分别贷 clearing 或 bank。若选择结算前不入账，则即时可用必须另外建模为平台垫资。

**5. P0｜§4.3、§5.2–5.4：事务边界和锁协议不足以保证不超额支出**

- **问题：** 锁余额行只是起点，没有规定所有改变可用余额的路径必须遵守同一协议，也没有明确余额、分录、hold、状态必须一起提交。
- **失败场景：** worker 先提交释放 hold，再扣客户余额；间隙中 P2P 花掉这笔钱。或者可用性释放与退回分别更新不同记录，出金读取到混合状态后通过检查。
- **建议修改：** 统一锁协议，覆盖出金、P2P、退回、限制释放、冻结和调账；涉及多个客户时统一排序。账内变更必须同一数据库事务提交，银行 HTTP 调用放在事务外。状态转换加行锁或版本比较；锁定后再读取参与计算的数据。

**6. P0｜§4.2–4.3：宣称的数据库不变量并没有被完整强制**

- **问题：** `sum(amount)=0` 只保证数值平衡；INSERT-only 也不等于 journal 永久封闭。
- **失败场景：** 往昨天的 journal 再追加一组平衡 postings，历史交易被改变，但 UPDATE/DELETE 权限和求和检查都不会阻止。空 journal、零额 posting、缺失 dedupe key 也没有明确约束。
- **建议修改：** 采用单一受控记账入口，在一次事务内完成完整 journal、余额更新和封账，禁止以后追加 posting。补充必要的 NOT NULL、至少两条非零 posting、币种与账户一致、业务金额与 posting 一致等约束。余额表应同步维护，五分钟重算只能作为侦测手段。

此外，数据库不能识别“哪个 Python 模块在执行 SQL”。§3.3 的数据库强制承诺需要改为具体的角色和数据库函数权限设计；其引用的 §4.4 实际是测试方法。

**7. P0｜§5.1、§6.1、§7.2：unknown 的恢复规则有资金释放漏洞**

- **问题：** “查单为空”没有被定义成何种强度的证据；hold 有 `expires_at`，却没有禁止 unknown 时自动过期。正文说不重发，状态图又允许回 held 重提。
- **失败场景：** 请求已被银行接受，响应丢失；查单暂时为空，系统释放 hold，客户再次出金，随后第一笔也结算。
- **建议修改：** unknown 不得因 TTL 或普通负向查询结果释放资金。持久化原请求参数及幂等键，按适配器合同恢复；明确幂等键有效期、查询语义和人工处置条件。Increase 官方明确建议用**原参数、原幂等键重试**，不建议依赖 list 查询构造自动恢复逻辑。[Increase 幂等文档](https://www.increase.com/documentation/idempotency-keys)

**8. P0｜§2.1–2.2、§8、§12：公开演示缺少可执行的隔离模型**

- **问题：** “只能影响自己的账户”与杀共享 worker、共享模拟银行、跨访客 P2P、全局调账及 kill switch 没有形成一致权限模型。
- **失败场景：** 访客反复触发杀 pod，让所有人出金进入 unknown；A 把演示资金转给 B，再重置自己的数据，破坏全局资金解释；机器人审批允许访客间接修改共享科目。
- **建议修改：** 每个演示空间具有服务端确定的 `demo_space_id`，贯穿数据库、消息、银行资源映射、演练和 AI 工具。首版只允许空间内 P2P。公开演练使用按 transfer/space 注入的故障；真实 pod kill 和全局开关仅作者可用。跨空间外键和对象授权需要服务端强制。

**9. P1｜§5.1、§6.1–6.3：内部状态没有与真实银行语义对齐**

- **问题：** API 受理、网络提交、结算和退回被压成简单状态链；`settled` 同时画成终态和可退回状态，也容易误导实现。
- **失败场景：** 等待银行发出不存在的 `settled` 状态，转账永久挂起；先处理 returned，后到的 submitted 又把状态退回。
- **建议修改：** 给每个适配器列状态与会计事实映射，分别保存提交、结算、退回事实。Increase 的 ACH Transfer **没有 `settled` 状态**，结算看 `settlement.settled_at`；退回可能提前到达，但仍会产生原支付及退回两笔交易。[Increase ACH 生命周期](https://www.increase.com/documentation/sending-ach-transfers)

**10. P1｜§3.2、§5.1、§events：outbox 和 Kinesis 只有名词，没有可靠性协议**

- **问题：** 未定义 relay 领取、租约、发布确认、消费者去重、checkpoint、毒消息和重放语义。§3.2 说 Kinesis 供下游消费，架构图却把它放在支付提交主路径。
- **失败场景：** 发布成功后 relay 崩溃，消息重复；先标记 published 再发送会丢消息；消费者先 checkpoint 后提交数据库会漏处理。批量部分失败后重试还可能改变业务顺序。
- **建议修改：** 明确按至少一次投递设计：固定 event ID、outbox 领取与恢复、逐条确认发布结果；消费者 inbox 去重与数据库副作用同事务提交，再推进 checkpoint。定义 aggregate version、重试上限、隔离队列和重放权限。外部出款仍依赖银行幂等。AWS 明确说明生产和消费重试都会重复，`PutRecords` 不保证顺序。[重复处理](https://docs.aws.amazon.com/streams/latest/dev/kinesis-record-processor-duplicates.html)、[PutRecords](https://docs.aws.amazon.com/kinesis/latest/APIReference/API_PutRecords.html)

**11. P1｜§5.2、§6.3：API 幂等、事件幂等与业务幂等混淆**

- **问题：** “幂等键校验”和 webhook event ID 唯一不足以保证同一笔业务只发生一次。
- **失败场景：** 两个并发 API 请求先后查不到 key，各生成 transfer；银行用不同 event ID 通知同一结算；查单与 webhook 同时触发入账。
- **建议修改：** API 用 `(主体/空间, 操作, key)` 唯一约束绑定请求摘要与原响应，同 key 不同参数拒绝。银行事件按 provider、环境及 event ID 去重；会计效果按 transfer 和业务效果再次去重，所有来源共用同一转换入口。唯一键冲突时核验已有内容，不能一律当成功。

**12. P1｜§5.3、§8：负余额、准备金和损失混成了一件事**

- **问题：** “记入费用科目的准备金视图”没有会计含义；演练又直接要求损失入账，时点不一致。
- **失败场景：** 用户把 $100 入金全部转走，退回后借客户／贷 bank 已形成 $100 客户借方余额；再随手借损失／贷 bank，会把银行现金扣两次。
- **建议修改：** 明确负余额是客户应收的业务展示，费用确认另有政策。例如退回后，将客户借方余额重分类为应收；确认不可收回时借损失／贷应收。若实现预计信用损失准备，则另设抵减资产科目，不能与实际核销混用。

**13. P1｜§4.3、§7：对账口径可能重复计算在途，也缺乏独立性**

- **问题：** 银行 FBO 与内部 `bank:fbo` 对账时又写“±在途”，没有定义何时内部现金已经记账；“客户负债 = 现金 ± 在途”也漏掉损失、应收和平台资金。
- **失败场景：** 内部 bank 只按已入账银行交易更新，本来应与银行 posted balance 相等，再减一次出金在途，制造假差异。反过来，模糊的“在途”又能掩盖真正漏账。
- **建议修改：** 固定报告时点和 balance 类型，给每个调整项写明确公式及来源。分别检查总账恒等式、客户负债与资产覆盖、银行现金对账。银行侧使用独立拉取的交易/对账数据；支持冻结输入快照、分页断点、重叠扫描及幂等差异记录。Trace number 不能单独充当全局唯一键。[Increase 对账说明](https://www.increase.com/documentation/ach-returns)

**14. P1｜§5.3、§5.5：ACH 退回规则表述过度简化**

- **问题：** “消费者可以在 60 天内以 R10 退回”方向基本正确，但未说明起算点、条件和其他时限，容易被实现成第 61 天绝对安全。
- **失败场景：** 用发起日代替结算日起算，提前关闭退回处理；把金额不符都标 R10；把未授权退回当普通失败自动重扣。
- **建议修改：** 分开写普通退回时限与消费者未授权借记的扩展窗口；后者通常以结算日起算 60 个日历日，并涉及 WSUD。R10 是无授权，R11 是有授权但扣款不符合授权。Reg E 的报错期限另从相关账单发送日起算，不能混用；还要保留迟到退回处置路径。[银行规则说明](https://docs.crossriver.com/concepts/returns-and-reversals)、[Nacha R10/R11](https://www.nacha.org/rules/differentiating-unauthorized-return-reasons)、[CFPB §1005.11](https://www.consumerfinance.gov/rules-policy/regulations/1005/11/)

**15. P1｜§1.1、§5.5、§6：资金方向、授权与 Same-Day ACH 缺少最小领域模型**

- **问题：** 从产品视角把拉钱叫“入金”没错，但对 Increase 而言它是自己发起的 **outbound ACH debit**；工资才是 inbound credit。Plaid 绑定也不等于获得扣款授权。
- **失败场景：** 适配器按“入金”选择 inbound API；账户绑定成功就发起借记；周五错过银行 cutoff，仍展示当天可用。
- **建议修改：** 分开保存产品资金方向、ACH debit/credit、网络 origination direction、SEC code、授权记录及银行来源。区分银行 cutoff、FedACH 窗口、结算时间和客户资金可用时间。Same-Day 同时支持符合条件的 credit/debit，并不消除退回风险。按文档日期，单笔上限仍为 $1M；$10M 到 2027-09-17 才生效。[Increase 借记要求](https://www.increase.com/documentation/sending-ach-debit-transfers)、[FedACH 时间表](https://www.frbservices.org/resources/resource-centers/same-day-ach-resource-center/fedach-processing-schedule/)、[Nacha 上限变更](https://www.nacha.org/rules/increasing-same-day-ach-dollar-limit-10-million-0)

**16. P1｜§5.3、§6：客户可用余额与银行可出款流动性没有区分**

- **问题：** 老用户“小额即时可用”只定义了客户额度，没有定义平台拿什么现金垫付，也没考虑银行自身的 ACH debit hold。
- **失败场景：** 所有客户余额都足够，但共享 FBO 可用余额被银行 hold 占满，出金批量失败；演示以为是状态机问题，实际是平台流动性不足。
- **建议修改：** 分开维护客户 posted/available、银行 current/available、平台垫资额度和全局出款容量。即时可用配置必须受已注资准备资金限制。Increase 默认会对 ACH debit 入账施加 funds hold，更快可用需要另行安排 reserve。[Increase funds holds](https://www.increase.com/documentation/sending-ach-debit-transfers)

**17. P1｜§6.2、§8、§11：fault-proxy 可能制造错误的银行事实**

- **问题：** 网络故障注入与模拟银行业务状态没有明确分界；§6 强调真实 sandbox 行为，§11 又引入未定义的模拟银行。
- **失败场景：** 请求已经成功转发，proxy 却伪造“银行拒绝”，内部退款，sandbox 随后照常出款。只观察本地状态的测试反而可能通过。
- **建议修改：** 分开“真实 sandbox＋传输故障”和“确定性模拟银行＋业务状态故障”。伪造未受理拒绝必须确保未转发请求；转发后丢响应只能进入 unknown。对两者执行适配器契约测试，报告明确说明运行模式。

**18. P1｜§2.2、§9、§12：AI 和公开内部视角的授权边界不足**

- **问题：** 只读工具、脱敏和 viewer 角色没有覆盖对象授权、敏感原文及提示注入；机器人审批也不能证明独立审批控制。
- **失败场景：** 访客诱导 AI 查询其他空间的 transfer，缓存又把调查结果分享给下一位访客；银行请求原文展示出 token 或签名头；恶意交易描述让 AI 起草错误调账。
- **建议修改：** 工具服务端从会话注入空间和权限，不能信任模型提交的身份；工具输出及公开调查链使用字段白名单，缓存包含授权范围。AI 草稿限制可选科目和金额，审批绑定不可变内容摘要，禁止自批。机器人审批只用于隔离体验，页面明确标注为模拟。

**19. P1｜§9.3、§15.2：AI 成本限制无法保护总预算**

- **问题：** 每 IP、每会话次数限制可被换 IP/新会话绕过，单次调查的 token 和工具调用次数也没有上限。
- **失败场景：** 攻击者不直接问 AI，而是不断制造差异触发自动分诊；长时间线加多轮工具调用让几次请求耗尽月预算。
- **建议修改：** 增加全站每日/月度硬预算、并发上限、token 和工具步数上限、自动任务配额及重试上限。请求开始前原子预占最坏成本，结束后结算；预算耗尽切换预生成报告。公开访客默认不触发昂贵模型自动升级。

**20. P1｜§4、§6.3、§12：24 小时清理与不可变账本、迟到事件冲突**

- **问题：** 未定义“清理”究竟删除什么，也没有演示注资和重置的会计规则。
- **失败场景：** 删除客户后银行才发来退回，事件无法关联；删除历史 journal 后 FBO 仍有余额；保留 dedupe key 但删处理结果，重放行为失去依据。
- **建议修改：** 24 小时后关闭访问、删除可识别展示资料；交易关联、幂等记录和必要审计按独立策略保留。演示空间采用独立账套或明确的归档机制。初始 $100 必须有对手科目及银行模拟注资，重置不得靠直接改余额。

**21. P1｜§12–13：公开站点缺少基本 Web 安全与恢复设计**

- **问题：** WAF 和源站共享头不能替代会话、CSRF、对象授权及输出安全；“不收真实 PII”也无法靠识别号码外观实现。长期运行却没有备份恢复目标。
- **失败场景：** 用户把真实资料填进自由文本；交易备注形成存储型 XSS，影响同源博客；数据库误删后只剩 Grafana 截图，无法恢复账本。
- **建议修改：** 身份数据由服务端生成，SSN 不接受自由输入；补充安全 cookie、CSRF、CSP、输出编码、敏感响应禁止共享缓存、后台入口隔离。明确备份/PITR、RPO/RTO，以及恢复后的事件重放和账本校验流程。

**22. P1｜§3、§13.2、§14：范围与预算尚未成为可执行约束**

- **问题：** 一个人同时承担两家银行、Plaid、KYC、完整运营后台、六类演练、三套可观测数据系统和 AI，交付面过宽；$150–250 只有控制面成本有依据。
- **失败场景：** M0 花大量时间搭平台，面试前仍没有一个可信的退回场景；两个小节点被监控组件挤满。私网节点取消 NAT 后，又无法访问银行、AI 或拉取所需资源。
- **建议修改：** 保留 EKS 这一既定选择，但把首版缩成：一个适配器、完整账务、对账、两个演练、一个带引用的 AI 调查。Column、完整 KYC、跨访客 P2P、Tempo/Loki 全套后移。预算逐项列节点、ALB、RDS、Redis、Kinesis、磁盘、备份、IPv4、流量、日志和 AI，并画清无 NAT 的出网方案。EKS $73/月只适用于标准支持；进入扩展支持后约 $438/月，仅控制面就超预算。[AWS EKS 定价](https://aws.amazon.com/eks/pricing/)

**23. P2｜§4.4、§8、§11：测试目标过于依赖“最后账平了”**

- **问题：** 借贷平衡和零重复 journal 都不能证明钱记给了正确的人；50 个协程也不能覆盖数据库崩溃和跨进程竞争。
- **失败场景：** 将 A 的钱贷给 B，所有 journal 仍平衡；漏记整笔转账也不会破坏平衡；出款成功后崩溃导致重复提交，只测数据库看不出来。
- **建议修改：** 使用独立参考模型验证每个客户和银行侧资金变化；在银行接收前后、DB commit 前后、发布前后、checkpoint 前后注入崩溃。覆盖 return 先到、查询与 webhook 竞争、unknown 超过 hold TTL、重启后重放。演练中的“恰好十笔成功”要明确指十笔预留受理，还是十笔银行出款。

**24. P2｜§10.3、§13.1、§14：若干承诺存在表达或落地矛盾**

- **问题：** 一个 trace 贯穿外部银行异步 webhook 没有实现依据；灰云回退不能继续维持原路径 Worker 路由；M2 可公开与安全隔离、对账和恢复后置矛盾。
- **失败场景：** 外部 webhook 没有原 trace context，调查链断裂；博客转灰云后 `/apps/fern` 直接落到 GitHub Pages；M2 上线后漏事件无人发现。
- **建议修改：** 用 transfer ID、银行 ID、event ID 建立长期关联，各阶段 trace 用 links 串联。Cloudflare 回退必须提前给出仍满足域名要求的具体方案，且补齐 `/apps/fern` 无尾斜杠入口；Workers Routes 要求对应域名处于代理模式。[Cloudflare Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/) 将最小隔离、幂等恢复和对账纳入首次公开上线门槛。另修正“一笔业务一个 journal”与多阶段 journal 的冲突。

**总体评价**

能引起这家公司工程师的兴趣：模块化单体、Postgres 权威账本、unknown、一致性检查、对账和有证据的 AI 调查，方向都贴题。

但按当前文档深入追问，会更像“知道应该有哪些组件”，尚不足以证明“能正确处理钱”。真正打动人的材料应是：**同一笔交易在超时、崩溃、乱序、退回后，银行事实、客户余额和总账仍能逐项解释**。一个完成的闭环，比第二家银行和更多看板更有说服力。

**最该先改的三件事**

1. **补齐资金会计规范：** 统一科目方向、余额符号，写出出金、拉款入金、工资入账所有状态及失败路径的分录、hold 和现金影响。
2. **补齐可靠性协议：** 明确数据库事务与锁、API/业务幂等、unknown 恢复、outbox/inbox、乱序事件和独立对账，配对应崩溃测试。
3. **缩小并隔离公开版本：** 一个银行、独立演示空间、两个可重复演练、全站成本硬上限；在上线前确认完整月度账单及出网方案。
